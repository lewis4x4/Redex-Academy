# F5 — Sim Engine Framework + Engines #1 (Branching) & #2 (Device-Config) + JSON Schemas

- **Effort tier:** ultracode
- **Phase:** 0 (Foundation)
- **HUMAN-GATE:** the engine public API + JSON Schemas are signed off by a human before any consumer (M3/M4/M5/M9/M10) builds against them (ledger §J). This is the program's #2 risk bet.

## Objective
Build the **shared sim framework** ("the Forge" umbrella per ledger §E) and the first two declarative engines — **#1 branching scenario** and **#2 device-config state-machine** — each with a published **JSON Schema + Zod** spec, validated against the framework's shared services. Authors write specs + choose fixtures; they never write a runtime.

## Reconciled engine model (ledger §E — AUTHORITATIVE; resolves the wave3 §5.1 vs experience-design §1.2 conflict)
There are **six engines**. The wave3 "4 data shapes" and the experience-design "Forge archetypes" are the **same engines** described two ways — build to **this** list:
1. **Branching scenario** (judgment/customer/egress-fail) — *this goal*.
2. **Device-config state machine** (Partner Portal, panel programming, OpenEye, DragonFruit static-IP) — *this goal*.
3. **WebGL 3D install** (R3F/Three.js; **Rapier physics deferred from MVP**) — built in M5.
4. **Virtual IQ-panel state machine** (XState) — Phase 2 (stub only here).
5. **Declarative 2D-interaction** (drag/label/match/sort/hotspot) — **F5b**.
6. **Parametric calculator** (PPF/DORI, PoE budget, retention, "will it hold") — **F5b**.

Experience-design archetypes map onto these: A. Terminate-&-Energize → #3; B. Place-&-Cover → #3/#6; C. Operate-the-Panel → #2/#4; D. Budget-&-Sequence → #6. The **2D "picture-book" fallback renderer is first-class**, not a degraded mode.

## Tasks (ordered)
### Shared framework (`packages/sim-engine`) — built once, used by all engines
1. Define the **engine public API** every engine implements (a stable TS interface): `loadSpec(spec, fixtureSet?) → SimInstance`; `SimInstance` exposes state (Zustand store), the interaction primitives, `getVerdict()`, telemetry subscription, and an i18n string resolver. Document it as the consumer contract.
2. Build the **Verdict service** (ledger §E, experience-design §1.5): a single service every sim calls to evaluate a build against its rubric line items, mapping to the §5.4 four dimensions. It owns: scoring math, the **safety-veto hook** (a `0` on any safety-flagged check ⇒ veto/fail, mirroring the DB rule), and the **feedback wording** (instant, specific, diagnostic — names the real-world consequence + the fix), so behavior is identical across engines and translatable.
3. Build the **shared xAPI telemetry emitter**: actor/verb/object/result/context statements, queued offline (Dexie) and flushed via F4's path; every meaningful interaction emits a statement with a `client_event_uuid`. (The LRS bridge itself is M8; F5 emits + queues.)
4. Wire the **offline cache contract** (spec + assets cache via F4 field packs), the **i18n string layer** (all sim strings keyed; EN+ES; safety glossary non-overridable), and **colorblind-safe state rendering** (shape + text + color — never color alone for pass/fail).
5. Build the **2D picture-book fallback renderer** primitives in `packages/sim-engine`/`packages/ui` (high-contrast schematic, same drag targets, same Verdict + scoring), usable by spatial engines as a true alternative path.
6. Provide a **preview/sandbox harness** that renders any valid spec (used by M9 authoring) and validates it against the JSON Schema + Zod before load.

### Engine #1 — Branching scenario
7. Author the **branching JSON Schema + Zod** in `packages/sim-schemas`: a scenario graph — `nodes` (situation/prompt, media refs, i18n keys), `edges` (choices → next node, consequence text, score delta, **`safety_flag`** for veto-relevant wrong branches), a `start` node, terminal pass/fail nodes, and a `verdictRubric` mapping choices to §5.4 dimensions/line items. Support the "failure is safe, instant, instructive" rule and the egress **post-mortem replay** (freeze at the trap, overlay the deciding choice + the code line, drop back to the decision — experience-design §1.4).
8. Build the **branching engine** runtime (one React component tree over the graph) consuming the schema, wired to Verdict + telemetry + i18n + colorblind-safe rendering, with the 2D-friendly layout.

### Engine #2 — Device-config state machine
9. Author the **device-config JSON Schema + Zod**: a declarative device — `screens`/`fields`/valid `stateSpace`, **`assertionRules`** (e.g., "partition entry delay > 0", "smoke zone = 24-hour fire", "front-door camera reassigned first") each tagged with a §5.4 dimension and an optional `safety_flag`, plus a `fixtureSetRef`. The engine evaluates state against rules and emits telemetry.
10. Build the **device-config engine** runtime: a rules-driven state machine over a simulated device UI that **replays a sanitized recorded fixture** (faithful interactive replica, never a live API). Define how the engine reads the fixture (consumes the `fixture_sets` R2 manifest — see the manifest contract below).
11. Define the **`fixture_set` R2 manifest schema** (consumed by engine #2 and M4): `version` (tied to a platform-manifest surface), `source` enum, ordered `screens` (image R2 keys + interactive hotspots/field maps), `sanitized: true` (publish gate), and a `source/citation` reference for accuracy audit. Publish it in `packages/sim-schemas`.

### Stub
12. Add a **placeholder export** for engine #4 (virtual IQ-panel / XState) so the API surface is reserved; full build is Phase 2.

## Done-criteria (testable)
- `packages/sim-schemas` publishes the **branching**, **device-config**, and **fixture_set manifest** JSON Schemas + Zod; invalid specs fail validation with clear errors.
- The engine public API + Verdict + xAPI emitter + offline cache + i18n + colorblind-safe rendering exist in `packages/sim-engine` and are documented as the consumer contract.
- **Verdict/safety-veto tests:** a fixture spec with a safety-flagged wrong branch/assertion triggers a veto → `fail` and sets `sim_attempts.safety_veto_triggered`; pass/fail/veto paths covered.
- A **reference branching sim** and a **reference device-config sim** (toy fixtures) run end-to-end in the preview harness, emit queued xAPI, and render in both the rich and 2D fallback modes.
- Telemetry events carry `client_event_uuid` and queue offline (verified with F4's harness).
- The **2D fallback** produces the same Verdict/score as the rich renderer for the same input.
- `[HUMAN-VERIFY]` engine API + JSON Schemas reviewed/signed off before M3/M4/M5/M9/M10 consume them.
