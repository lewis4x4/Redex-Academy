# F6 — OB 3.0 Issuer + Key Management + Status List

- **Effort tier:** ultracode
- **Phase:** 0 (Foundation)
- **HUMAN-GATE:** key custody + proof suite + server-only signing reviewed; "badge verifies at a public URL" `[HUMAN-VERIFY]` (ledger §J).

## Objective
Build the Open Badges 3.0 / W3C Verifiable Credentials **issuer**: construct + sign a credential, publish a hosted verifiable assertion + the issuer `.well-known` profile, maintain a hosted **status list** for revocation, and define key rotation. **Resolve the Deno-vs-Node signing decision explicitly** (ledger §F) before wiring the signer.

## Depends on
- **F2** (`badge_classes`, `credentials` with `open_badge_json`/`proof`/`hosted_assertion_url`/`status`; generated types).

## Consumes (contracts)
- `academy.badge_classes` (`requires` for stackability), `academy.credentials`.
- `.env` names: `OB_ISSUER_DID`, `OB_ISSUER_PRIVATE_KEY`, `OB_ISSUER_PUBLIC_KEY`, `VITE_OB_ISSUER_PROFILE_URL`.
- `workers/` (Cloudflare) for the public verify/profile endpoints; Supabase Edge Functions (Deno).

## Pinned decisions (ledger §F — implement exactly)
- **Proof suite:** `eddsa-rdfc-2022` / **Ed25519** (Data Integrity proof).
- **Issuer:** `did:web:academy.redex.education` (reconciled in F6 from the placeholder `goredex.com` — the product is hosted at `redex.education`; see `CLAUDE.md` §5a + `adr/ADR-0005` addendum) — the issuer profile lists **current + retired** keys to survive rotation.
- **Status list:** a hosted **BitstringStatusList** (a.k.a. StatusList2021) the verifier checks for revocation.
- **Key custody:** **Supabase Vault** (co-located with the `issue-badge` Edge Function) — single location; never in the client bundle or repo; never both Vault and CF Secrets.

## REQUIRED DECISION — Deno vs Node signing (ledger §F; make it in this goal, document it)
Edge Functions run on **Deno**. Either:
- **(A)** Use a **Deno-compatible** Ed25519 / Data-Integrity VC signing library inside the `issue-badge` Edge Function; **or**
- **(B)** Run issuance in a dedicated **Node context** (a Cloudflare Worker/container microservice) if no Deno-compatible lib meets the proof-suite requirement.

Do **not** assume a Node-only library works in a Deno Edge Function. Evaluate a Deno-compatible signer first (prefer A for co-location with Vault custody); if it cannot produce a conformant `eddsa-rdfc-2022` proof, fall back to B and document why. **Record the chosen path + rationale in the PR and in `CLAUDE.md`.**

## Tasks (ordered)
1. **Make and document the Deno-vs-Node decision** above; pick the signing library accordingly.
2. Define the **credential JSON-LD shape**: an OB 3.0 `AchievementCredential` / W3C VC with `credentialSubject` (recipient `achievement`), `issuer` (the DID), `evidence` (links to `signoff_evidence`/job records), `issuanceDate`/`expirationDate`, `credentialStatus` (the BitstringStatusList entry), and the `proof`. Publish the shape as a typed builder in a shared package so M7 reuses it.
3. Implement the **`issue-badge` Edge Function** (or the Node microservice per the decision): builds the credential, **signs server-side only** with the Vault-held key, writes `credentials` (`open_badge_json`, `proof`, `hosted_assertion_url`, `status='active'`), and publishes the hosted assertion to R2/Worker. **Signing never runs on the client.**
4. Implement the **Cloudflare Worker** endpoints: the public, always-on **hosted assertion URL** (verifiable), the issuer **`.well-known` / DID document** profile (lists current + retired keys), and the **status list** endpoint.
5. Implement **revocation**: flipping `credentials.status` to `revoked`/`recert_required` updates the published status list so a verifier sees the change (required for "badge earned on a retired version flips to recert required").
6. Define the **key-rotation plan**: generate/retire keys, the issuer profile carries both, old proofs still verify against the retired key. Document the runbook.
7. Wire a conformance check (an OB 3.0 / VC verifier) into tests.

## Done-criteria (testable)
- The Deno-vs-Node decision is **made and documented** (PR + `CLAUDE.md`); the signer matches the chosen path.
- A test badge is **issued, signed (`eddsa-rdfc-2022`/Ed25519), and verifies** against an OB 3.0 / VC verifier in CI.
- The hosted assertion URL, the `.well-known`/DID issuer profile (current+retired keys), and the status-list endpoint are all reachable.
- **Revocation test:** flipping status updates the status list; the verifier reports the credential as revoked.
- **Signing-location test:** issuance/signing is unreachable from any client path (server-only); the private key never appears in a client bundle.
- `[HUMAN-VERIFY]` a human confirms a real issued badge **verifies at a public URL**, reviews key custody + the proof suite + the rotation runbook before release.
