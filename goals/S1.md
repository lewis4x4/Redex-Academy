# S1 — MVP-Slice Catalog Seed + AC-203 Line-Items + Badge_Class Defs

- **Effort tier:** ultracode
- **Phase:** Seed

## Objective
Seed the MVP-slice **catalog** (courses, units, competencies, prerequisite edges, course_versions) for the Access Control entry-through-egress slice, the **§5.4 line-items for AC-203** (its ~6 safety lines + non-safety lines), and the **badge_class** definitions (with stackability `requires`) the slice issues. This is content-as-data that unblocks M1/M2/M3/M4/M5/M6/M7.

## Depends on
- **F2** (catalog + competency + prereq + assessment + badge tables, enums, DAG check) and **F2a** (so the `workos` join exists for the M6 sign-off path; demo `workos.jobs` rows are linkable).

## Consumes (contracts)
- `academy.courses`/`course_versions`/`units`/`competencies`/`unit_competencies`/`course_prerequisites`/`course_platform_dependencies`, `academy.assessment_items` (with `is_safety_item`), `academy.signoff_line_items` (the line-item key catalog), `academy.badge_classes` (with `requires`).
- Generated types from F2/F2a. The DAG check (must stay acyclic).

## The MVP slice (ledger §D — prereq-closed; seed EXACTLY these 14 courses)
`FND-101, FND-102, FND-103, INT-101, INT-102, ADC-101, ADC-102, ADC-201, AC-101, AC-102, AC-103, AC-201, AC-202, AC-203`.

### Prerequisite edges to seed (from the Course Bible, with the ledger §D closure fixes)
- `FND-102 ← FND-101`; `FND-103 ← FND-102`.
- `ADC-101 ← FND-101` (light Foundations); `ADC-102 ← ADC-101`; **`ADC-201 ← ADC-102, INT-101`** (closure: ADC-201 needs ADC-101/102 — include them so ADC-201 is reachable).
- `AC-101 ← FND-101` (+FND-104 recommended; FND-104 not in slice → seed as `soft` or omit); `AC-102 ← AC-101`; `AC-103 ← AC-101, AC-102`.
- **`AC-201 ← AC-101, AC-102, AC-103, FND-102, FND-103` + `ADC-201` (hard_gate — the missing edge per ledger §D)**.
- **`AC-202 ← AC-201, FND-103`**; **`AC-203 ← AC-201, AC-202, AC-103` + `FND-102` (safety gate)** — closure: AC-203 needs AC-202 (was missing).
- INT: `INT-101 ←` (entry); `INT-102 ← INT-101`.
- Mark `hard_gate` vs `soft` per the bible; the seeded graph MUST pass the F2 DAG check.

## Tasks (ordered)
1. Author a **deterministic, idempotent seed** (SQL or a typed Supabase seed script in `supabase/seed/`) that upserts the 14 courses with their canonical codes, titles, domains, tiers, personas, and one published `course_version` each (SemVer `1.0.0`, with a `platform_manifest` where relevant — e.g., AC-201 Aero X1100; AC-202 Mercury LP1501/LP1502).
2. Seed the **competencies** the slice grades against (e.g., `EGRESS.MAGLOCK_FAILSAFE`, door-anatomy, credential/lock-family selection, Aero single-door commissioning, Mercury wiring, PoE/voltage-drop) with `is_safety_critical` set correctly (egress/fail-state competencies = true).
3. Seed **units** per course mapped to the engine kinds (so M2–M5 have spec slots): AC-101 → 2D-interaction (drag-label anatomy + order the access event); AC-102 → 2D-interaction (match "Spec the Door"); AC-103 → branching ("Trapped or Free?"); AC-201 → device-config (Aero) + WebGL Virtual Door; AC-202 → calculator ("will it hold"/PoE) + device-config (Mercury); AC-203 → branching (egress-fail, mandatory) + WebGL (mag-lock/REX/fire-interface build). Map `unit_competencies`.
4. Seed **assessment_items** for the knowledge checks with `is_safety_item` set (ledger §C): AC-102 fail-safe/fail-locked items and all AC-103/AC-203 egress items = `is_safety_item=true` (→ ≥90% gate); others ≥80%.
5. **Seed the AC-203 §5.4 line-item catalog** into `signoff_line_items` key definitions (the per-course line-item keys + `is_critical_safety` flags; from Course Bible AC-203). The **critical-safety (⚠) lines** (`is_critical_safety=true`):
   - `ac203.release_on_power_loss` — door releases on power loss.
   - `ac203.push_to_exit_30s` — releases on push-to-exit for the full ≥30 s.
   - `ac203.release_on_fire_alarm` — releases on fire-alarm activation.
   - `ac203.pte_mount_40_48in_5ft` — push-to-exit mounted 40–48 in., within 5 ft, signed.
   - `ac203.no_maglock_defeat_fire_latch` — mag lock not used to defeat positive latching on a fire-rated door.
   - `ac203.emergency_lighting_present` — emergency lighting present.
   - `ac203.ahj_confirmed` — AHJ confirmed.
   - **Non-critical** lines (dimension-scored, `is_critical_safety=false`): `ac203.tech.fail_safe_wiring`, `ac203.tech.rex_fire_terminated`, `ac203.tech.supply_battery_sized` (Technical Execution); `ac203.verify.three_release_modes_logged` (Verification); `ac203.indep.recognize_no_maglock_escalate` (Independence). (Also seed AC-201/AC-202 line-items analogously from the bible for completeness of the slice sign-offs.)
6. **Seed `badge_classes`** for the slice with stackability `requires` (ledger §D credential-as-prerequisite + wave3 §3.7):
   - Skill badges: *Single-Door Aero Commissioning* (AC-201), *Mercury LP1501/LP1502 Wiring* (AC-202), *Mag Lock + REX + Egress Wiring* (AC-203, gating). Each `requires` its competency + a `field_proven` sign-off.
   - Tier credential: **Certified Technician — Access Control** with `requires` = the slice's skill badges (incl. AC-203), `kind='tier'`, with `recert_months` and `is_compliance` set for the egress 12-mo rule. Encode the **auto-issue** rule intent (tier credential auto-issues when component skill badges are all `field_proven` — ledger §D; the resolver runs server-side, defined in M7).
7. Provide the **credential-as-prerequisite resolver scaffolding** data: ensure aggregate gates like "Certified Technician — AC" exist as a `badge_class` so a Postgres function/view can resolve held credentials (the resolver itself is wired in M1/M7; S1 supplies the data it reads).
8. Re-run the DAG check; confirm acyclic. Seed must be **re-runnable** (idempotent upserts).

## Done-criteria (testable)
- Running the seed populates exactly the 14 slice courses, their versions/units/competencies, the prereq edges (incl. the `AC-201 ← ADC-201` and `AC-203 ← AC-202` closure edges), the AC-201/202/203 line-item catalog, and the slice `badge_classes`.
- The seeded `course_prerequisites` graph **passes the F2 DAG check** (no cycles).
- The AC-203 critical-safety line items are present with `is_critical_safety=true` (the 7 ⚠ keys above); non-safety lines present with `false`.
- `Certified Technician — Access Control` exists with `requires` referencing the three slice skill badges.
- Re-running the seed is idempotent (no duplicates, no errors).
- Safety assessment items carry `is_safety_item=true` (verifiable for AC-102/AC-103/AC-203).
