# M1 — Catalog + Prereq-Gated Enrollment + Skill-Tree View

- **Effort tier:** ultracode
- **Phase:** MVP

## Objective
Build the learner catalog browse, the prerequisite-gating resolver (handling **both** prereq kinds — `hard_gate` course edges **and** credential-held gates), prerequisite-gated enrollment, and the skill-tree view that resolves locked/available/passed/mastered nodes from the seeded graph.

## Depends on
- **F2** (catalog/enrollment tables + RLS + types), **S1** (the seeded slice catalog, prereq edges, badge_classes).

## Consumes (contracts)
- `academy.courses`/`course_versions`/`units`/`course_prerequisites`, `academy.enrollments`/`unit_progress`/`competency_state`, `academy.credentials`/`badge_classes` (for credential gates).
- The S1 seed (the 14 slice courses + edges + the `Certified Technician — AC` badge_class).
- F3 auth (the `org_id`/`role` claims so RLS scopes reads).

## Tasks (ordered)
1. Build the **prereq-gating resolver** as a Postgres function/view (server-authoritative): for a given user + course, return `locked|available|passed|mastered`. It must resolve **two prereq kinds** (build-readiness review §1 M1 gap):
   - `course_prerequisites.kind = hard_gate` → all required courses must be `passed`/`field_proven`.
   - **Credential-held gates** → "Certified Technician — AC"-style aggregate prereqs resolved by checking held `credentials` (ledger §D credential-as-prerequisite resolver). Use the S1 `badge_classes.requires` data.
2. Build the **catalog browse** UI in `apps/web`: list slice courses with tier/domain/persona, gating state badges (locked/available/passed), colorblind-safe (shape + text + color). Mobile-first.
3. Build the **skill-tree view**: the prerequisite graph rendered as nodes/edges with locked/available/passed/mastered states; boss/gate nodes (AC-203 egress hard gate) wear a distinct heavier frame + ⚠ marker (experience-design §). Resolve states from the resolver.
4. Implement **prereq-gated enrollment**: a learner can enroll only in `available` courses; enrollment writes `enrollments` (`enrolled_via='self'`) via the allowed client path (RLS-permitted insert for own user/org) — **never** writing `competency_state` (server-only).
5. Wire **edge read-cache** consumption (D1/KV catalog cache per wave3 §2.4) for the browse/"what can I take next" path where available; Postgres remains authoritative.
6. Ensure all catalog reads respect RLS: published catalog is cross-tenant readable; personal enrollment/progress is own-org only.

## Done-criteria (testable)
- Locked/available/passed/mastered nodes **resolve correctly from the seeded graph**: e.g., AC-203 is `locked` until AC-201 + AC-202 + AC-103 are passed; AC-301-style credential gates resolve from held `credentials` (even though AC-301 is out of slice, the resolver path is tested with the `Certified Technician — AC` badge_class).
- A learner can enroll only in `available` courses; attempting to enroll in a `locked` course is rejected.
- The skill-tree renders the slice graph with the AC-203 gate node visibly marked; colorblind-safe.
- Cross-org reads of personal enrollment data return zero rows (RLS).

## Out of scope
- Lesson content / knowledge checks (M2), sims (M3–M5), sign-off (M6), badge issuance (M7).
- Writing `competency_state` or credentials (server-only — M6/M7).
- Authoring UI (M9).

## Invariants in play
- Inv. 2 (client may write own `enrollments` but never `competency_state`/`credentials`).
- Inv. 3 (RLS — published catalog cross-tenant; personal data own-org).
- Inv. 5 (consume the S1 catalog/badge data; do not invent catalog shapes).
- Inv. 7 (colorblind-safe gating states).

## Tests required
- **Unit/DB:** the resolver — course-edge gating + credential-held gating; AC-203 lock/unlock transitions.
- **e2e (Playwright):** browse → see gating → enroll in an available course → blocked on a locked one.
- **RLS-negative:** cross-org personal enrollment reads return zero rows.
- **a11y:** catalog + skill-tree pass axe; no color-only state.
