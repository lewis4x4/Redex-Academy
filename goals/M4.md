# M4 — Device-Config Sim (Aero/Mercury) on the Engine + Fixture

- **Effort tier:** standard
- **Phase:** MVP

## Objective
Ship the AC-201 device-config sim on the F5 device-config engine: the learner configures/commissions the ADC-AC Aero single door (and the Mercury bring-up step), driving a faithful replica fed by a **sanitized recorded fixture**; assertion rules + safety flags evaluate via the Verdict service.

## Depends on
- **F5** (device-config engine + JSON Schema + Zod + Verdict/safety-veto + xAPI + the `fixture_set` R2 manifest contract), **S1** (AC-201/AC-202 units + competencies + line-items), **M1** (enrollment/gating).

## Consumes (contracts)
- F5's device-config JSON Schema + Zod + engine API + Verdict service; the **`fixture_set` R2 manifest** schema.
- `academy.sim_definitions` (`kind='device_config'`, `fixture_set_id`), `academy.fixture_sets` (`sanitized` publish gate), `academy.sim_attempts`, `academy.sim_telemetry_events`.
- Worker-served signed fixtures (wave3 §5.3) — JWT-validated fixture streaming from R2.

## Tasks (ordered)
1. Author the **AC-201 device-config spec** (Aero edition): the Partner Portal commissioning flow applied here — bring the Aero X1100 controller online to Alarm.com, add the door/credential, scan-to-add reader + test credential. Declare the device screens/fields/valid state space and the **assertion rules** (e.g., "controller online before add", "front-door reader enrolled", "test credential verified") tagged to §5.4 dimensions; flag the egress-relevant ones (`safety_flag`) per AC-201's ⚠ line ("correct fail-state set for the door's egress role before energizing"). Validate against the F5 schema.
2. Author/declare the **Mercury bring-up** config step (the device-config portion of AC-202: host/network bring-up, reader protocol selection) as a device-config spec (the wiring/voltage parts are M5/M2-calculator; M4 owns the config-UI flow).
3. **Author and register a sanitized recorded fixture_set** for the Aero/Portal flow against the F5 manifest schema: ordered screens (image R2 keys + interactive hotspots/field maps), `version` tied to the platform manifest, `source` enum, **`sanitized=true`** (the publish gate), and a source/citation reference. (Capture is an SME/human process; M4 authors the manifest + wires replay. If no real fixture is available, ship a clearly-labeled placeholder fixture that still exercises the pipeline, and mark the real-capture as a content dependency.)
4. Wire the **device-config engine** to load the spec + replay the fixture via the Worker-served signed path; evaluate state against assertion rules through the Verdict service; emit xAPI (queued offline).
5. Enforce the **publish gate**: a fixture with `sanitized=false` cannot be served/published (the F1 `sanitized-fixture` CI gate + a runtime guard).
6. EN+ES strings; colorblind-safe state rendering; mobile-first; 2D-friendly.

## Done-criteria (testable)
- The learner **configures the door** in the Aero replica; **assertion rules + safety flags evaluate**: a correct commission passes; a misconfiguration (e.g., wrong fail-state / unverified credential) is rejected with specific Verdict feedback; a safety-flagged error triggers the veto.
- The sim **replays a sanitized recorded fixture** (never a live API); production credentials/tokens are never in the client.
- A fixture with `sanitized=false` is **blocked** from publish/serve (CI gate + runtime guard).
- Telemetry queues offline and reconciles; renders in 2D-fallback with identical Verdict.
- EN+ES; colorblind-safe.

## Out of scope
- The 3D Virtual Door wiring build (M5) and the "will it hold" calculator (M2 via F5b engine #6).
- The egress-fail branching judgment sim (M3).
- Field sign-off (M6), badge (M7), AI feedback (M10).
- Real fixture **capture/sanitization** (SME human process) — M4 wires the replay + manifest; capture is a content dependency.

## Invariants in play
- Inv. 1 (safety-veto via Verdict on safety-flagged assertions).
- Inv. 4 (offline telemetry; never fake a pass).
- Inv. 5 (consume F5's engine + fixture manifest schema; do not invent the fixture format).
- Inv. 7 (colorblind-safe; EN+ES).
- Security: no production-system contact; sanitized recorded fixtures only (wave3 §5.4/§10).

## Tests required
- **Unit:** AC-201 spec validates against the device-config schema; assertion-rule pass/fail/veto; fixture manifest validates against the F5 manifest schema.
- **e2e (Playwright):** commission the Aero door correctly → pass; misconfigure → rejected; safety-flag → veto.
- **publish-gate test:** `sanitized=false` fixture is blocked.
- **offline + a11y:** telemetry reconciles; axe + keyboard path; no color-only state.
