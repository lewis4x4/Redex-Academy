# M8 — xAPI → LRS + Postgres Summary Projection

- **Effort tier:** standard
- **Phase:** MVP

## Objective
Wire the `xapi-bridge` Edge Function so the sims' queued xAPI statements flow to the self-hosted LRS (the firehose), and a defined set of **milestone** statements project into Postgres summary tables (`sim_attempts`, `unit_progress`) that gate progression — with a registered xAPI statement profile so the two writers stay consistent.

## Depends on
- **F4** (the offline xAPI queue + `/sync`/flush path), **F5** (the shared xAPI emitter + the sims that emit). (M8 also serves the F5b/M3/M4/M5 sims.)

## Consumes (contracts)
- F5's xAPI emitter (statement shapes), the offline queue (Dexie).
- `academy.sim_attempts`, `academy.unit_progress`, `academy.sim_telemetry_events` (`client_event_uuid`).
- `.env` names: `LRS_ENDPOINT`, `LRS_KEY`, `LRS_SECRET`.

## Tasks (ordered)
1. **Register the xAPI statement profile** (build-readiness §2 gap): pin the verbs, activity types, the Redex extension keys, and — critically — the **milestone statement set** that projects to Postgres (e.g., `attempted`/`completed` with score, `safety-veto triggered`, `passed`/`failed`). Publish it as a versioned profile/vocabulary in the repo so emitter (F5) and projector (M8) agree.
2. Implement the **`xapi-bridge` Edge Function** (Deno): accept batched statements from the client, **forward to the LRS**, and **project milestone statements into Postgres** summary tables. The LRS statement carries a reference to the Postgres summary row for joinability (wave3 §4.3).
3. Make the bridge **idempotent** (keyed on `client_event_uuid` / statement id) so offline replays don't double-write — the LRS firehose and the Postgres summary stay consistent.
4. **Division of labor (wave3 §4.3 rule):** facts that gate progression or issue credentials live in **Postgres**; behavioral facts live in the **LRS**; milestone facts live in both with a cross-reference. Do not move gating off Postgres.
5. **Graceful degradation / test mocking (build-readiness §7):** the bridge degrades gracefully if the LRS is unreachable (statements stay queued); CI **mocks the LRS** so M8 isn't blocked on live infra.
6. Add a **consistency contract test**: a milestone statement projected to Postgres matches the LRS record (the projection mapping is correct).

## Done-criteria (testable)
- Sim telemetry **lands in the LRS** (or the CI mock) as profile-conformant xAPI statements.
- **Milestone facts gate in Postgres:** `attempt completed with score` and `safety-veto triggered` project to `sim_attempts`/`unit_progress` and drive gating — without querying the LRS for gating.
- Replaying a flush is **idempotent** (no duplicate LRS statements, no duplicate Postgres summary rows).
- LRS-unreachable → statements remain queued and flush later; gating still works off Postgres.
- The projection consistency test passes (LRS milestone ↔ Postgres summary).

## Out of scope
- The sims themselves (F5/F5b/M3/M4/M5) — M8 transports what they emit.
- AI analytics / authoring quality dashboards (Phase 2) and the manager/exec dashboards (M11/Phase 2).
- Standing up the LRS host (Phase 0, human) — M8 integrates against `LRS_ENDPOINT`; CI mocks it.

## Invariants in play
- Inv. 4 (offline xAPI queue; idempotent flush keyed on `client_event_uuid`).
- Inv. 2 (gating facts in Postgres are server-authoritative; the LRS never gates credentials).
- Inv. 5 (consume F5's emitter shapes + the registered profile; do not invent statement shapes).

## Tests required
- **Unit:** the projection mapping (milestone statement → summary row); idempotency on replay.
- **Integration (mocked LRS):** statements forward; milestones project; LRS-down degradation.
- **Contract:** LRS record ↔ Postgres summary consistency.
